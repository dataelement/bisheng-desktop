# Web CI production inputs

The workflow calls [prepare-web-ci-inputs](../scripts/prepare-web-ci-inputs.mjs) with one absolute, new output directory. It produces node_modules, office and ppt directories for the portable assembler, plus verification.json. Supported build hosts are ordinary Node 24.15.0 on Windows x64 or macOS arm64/x64. Linux Office inputs and Electron-as-Node are rejected.

Preparation copies the maintained package manifest, authoritative npm lock, packages, scripts and atomic patches into a unique staging directory under that output. Credentials, node_modules, caches, Git metadata and package archives are excluded. Local file dependencies must name their expected package beneath the copied packages tree; missing/mismatched packages fail before installation.

Production installation runs npm-cli.js through process.execPath with ci --omit=dev --ignore-scripts and the project .tmp/npm-cache. Only literal legacy-peer-deps/install-links booleans are read from the maintained project npm configuration and passed as explicit lock-shaping flags; registry/auth configuration is never copied. This preserves the existing lock semantics rather than silently resolving a different peer graph. It does not execute a PATH npm shim or root Desktop postinstall. Every atomic patch is replayed using the installed build checkout's patch-package entry; missing patch targets and replay errors fail preparation. The authoritative lock bytes must remain unchanged. Brand installation runs separately against staging and requires the maintained icon/light/dark assets. Electron installation is not part of this production tree.

PPT generators execute through absolute maintained source script paths with staging as cwd and a fresh template output directory. The existing Office, PPT and workbench package builders consume that copied project and produce complete native Web packages. No Downloads directory, pre-existing offline base, copied Profile or prebuilt root cache is accepted as an implicit runtime input. Build tooling can use the checkout's installed tool closure, while generated output and the production dependency tree remain separate.

Production links are recursively validated before each copy. Their real targets must stay within the clean installed modules tree or explicitly approved local package roots, and expected local package links cannot change owners. Cyclic links, excluded private targets and outside paths fail. The final modules tree contains materialized files without .bin symlinks. It replaces the workbench package with its Web projection and removes the separate Desktop PPT core and the source Office/PPT adapters; the complete Web Office and PPT packages are delivered through their explicit sibling input directories.

The output must be absent and may not overlap repository inputs or traverse an existing symlink ancestor. Success removes only the verified invocation-owned staging directory. Failure retains staging for diagnosis and writes status=failed without any ready claim. Verification JSON contains hashes, target/version, stage booleans and template counts, without credentials or absolute user paths. Child tool output is not forwarded because dependency tools can print registry credentials.

status=prepared means production input preparation succeeded. runtimeAcceptance=false remains explicit: the portable assembler must still verify archive integrity, actual bundled Node startup, Profile dependency closure, authenticated HTML/bootstrap and Office/PPT imports. This step does not publish, dispatch Actions, sign or deploy.

Behavior tests are in [web-runtime-ci-inputs.test.mjs](../test/web-runtime-ci-inputs.test.mjs). They exercise rejected output paths, source filtering, materialized local dependencies, missing package inputs, hostile links/owner changes/cycles and actual npm CLI selection.
