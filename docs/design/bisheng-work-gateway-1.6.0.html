02 / 加密与签名：保护三件事

传输与本地凭据

数据不明文传输

HTTPS 保护登录票据、token、查询和文档传输；部署时验证服务端证书。

Work 已使用系统 safeStorage 加密保存凭据，由主进程负责读取与刷新，不向界面和模型返回 token。

厂商授权 · 已有 RS256

企业授权不可自行篡改

厂商持签名私钥，Gateway 持验签公钥。校验签名、签发方、用途、有效期及既有授权绑定。

新增 API bit 须升级签名 schema；旧授权未包含该权限时，知识库 API 默认关闭。不能只改数据库开通。

内部请求 · 已有 HMAC-SHA256

确认请求来自可信服务

签名覆盖方法、路径、正文摘要、keyId、时间戳和随机 nonce；校验 ±60 秒时间窗，Redis 原子去重防重放。

服务密钥仅部署在服务端，按调用方向隔离；知识库请求拟沿用这一机制。

HTTPS 负责保密，签名负责验真与防篡改。JWT 编码不等于加密。旧 License 外层 RSA 解密也不能替代内部 RS256 授权验签。

实现边界与代码依据

Gateway 基准 v1.6.0@8f9390b0：DshEntitlementService、DshServiceAuth、DshJwtService。桌面凭据：src/main/enterprise/secure-credential-vault.ts。

当前 HMAC 正文上限 64 KiB，不能直接用于整份大文件。上传后续采用受签名保护的上传元数据与文件摘要，并在服务端校验实收内容。

HMAC 是服务间共享密钥认证，不能作为厂商授权签名的替代品。未假定已有 mTLS 或额外应用层 AES 正文加密。

03 / 从企业登录到一次知识检索

  1. Work → 企业 SSO

    系统浏览器完成登录，使用一次性身份票据 + PKCE；Work 主进程核对登录 state。

  2. Work → Gateway

    提交票据与 PKCE verifier。Gateway 校验并通过内部签名调用向 Bisheng 兑换真实员工身份，确认已分配席位。

  3. Gateway → Work

    签发短期 access token 与轮换 refresh token。主进程保管凭据，插件仅获得连接状态。

  4. Work → Gateway

    插件通过 Broker 请求检索；Gateway 校验 token 的签名、用途、有效期与当前 session，再检查企业 API 权限和该用户的有效席位。

  5. Gateway → Bisheng

    网关从认证结果获取企业、员工身份，写入受 HMAC 保护的内部请求；丢弃客户端自报身份。Bisheng 验服务签名，再按员工 ACL 检索。

  6. Bisheng → Work

    经 Gateway 返回可见片段与引用，由当前 Agent 生成回答；打开引用再次鉴权，上传额外校验写权限。

已有：SSO / PKCE、短期 token、refresh 轮换及服务 HMAC。待新增：知识 API token 合同、API bit 准入与可信员工知识接口。

Token 兼容性

现有桌面 access token 使用 HS256，audience 为 bisheng-dsh-model。不能直接当知识 API token 使用；实施时须版本化扩展用途与校验合同，知识路由拒绝旧模型 token。refresh 轮换沿用现有重用检测。

04 / 商业授权只保留一条规则

开通 Connect = 登录会话有效 ∧ 企业已购知识 API 权限 ∧ 当前用户有有效 Work 席位
实际访问 = 已开通 Connect ∧ Bisheng 当前资源权限。

拟新增权限 WORK_KNOWLEDGE_API，具体 bit 编号实施时确认。每次 API 调用由 Gateway 检查当前授权与席位；前端显示状态不能作为放行依据。

保留 Connect 入口，显示“企业未开通知识库 API”，联系管理员。

已购买、有席位

v1.6.0 既有基础席位同样可满足席位条件，但不自动获得 API 购买权限。此授权针对 Work 企业接入；Bisheng 开源知识库能力保留。首期做检索与引用，上传随后接入同一认证链。
