01 / 整体架构：三条策略通道

所有请求 → HTTPS → 路由策略注册表 → 对应认证与授权 → 业务处理
按路径与 HTTP 方法确定通道，不能根据客户端自报类型选择较宽松策略。DSH 路由优先于普通版本路由匹配。
A / 普通请求

Web 与第三方集成

/api/v1/**、/api/v2/** 及其他已登记普通版本路由，排除 DSH 路径。

Gateway 公共流量策略 → 透传 Bisheng。

Bisheng 校验：Web 登录或 OpenAPI Bearer、scope、企业与资源 ACL。

不增加 DSH 席位要求。普通不等于匿名；DSH token 不能作为 v2 凭据使用。

B / DSH 请求

Work 与企业插件

目标 /api/dsh/**，历史 /api/v1/dsh/** 显式进入同一策略。

Gateway 统一基础切面：认证 → session → DSH 授权 → 有效席位 → 操作功能 bit。

通过后才进入受控适配：模型调用 DSH 服务，知识库复用 v2 OpenAPI。

所有桌面业务必须经过该切面；未登记业务路由默认拒绝。

C / 原有商业能力

Gateway 企业扩展

现有 SSO、组织同步、敏感词等，如 /api/oauth2/*、/api/group/*、/api/sensitive/*，逐端点登记。

对应 License / 功能授权 + 原有管理或服务认证 → Gateway Controller。

默认不要求 Work 席位。挂载在普通透传链上的商业过滤器按能力启用，授权到期不阻断免费核心。

License 状态、健康检查、登录回调、内部服务调用单独声明策略。不能用“非 v1/v2 路径”代替商业功能清单。

厂商签名授权 → Gateway 公钥验签
拟在签名授权中增加企业知识库 API 权限位；企业管理员在有效授权范围内分配 Work 席位。

02 / 加密与签名：保护三件事

传输与本地凭据

数据不明文传输

HTTPS 保护登录票据、token、查询和文档传输；部署时验证服务端证书。

Work 已使用系统 safeStorage 加密保存凭据，由主进程负责读取与刷新，不向界面和模型返回 token。

厂商授权 · 已有 RS256

企业授权不可自行篡改

厂商持签名私钥，Gateway 持验签公钥。校验签名、签发方、用途、有效期及既有授权绑定。

新增 API bit 须升级签名 schema；旧授权未包含该权限时，知识库 API 默认关闭。不能只改数据库开通。

内部请求 · 已有 HMAC-SHA256

区分两种服务调用

已有 DSH 内部认证使用 HMAC：方法、路径、正文摘要、keyId、时间戳与 nonce；±60 秒窗口及 Redis 去重防重放。

知识库复用 v2 Bearer + delegate / X-On-Behalf-Of，不额外叠 HMAC。密钥仅留服务端，委托员工从已认证会话确定。

HTTPS 负责保密，签名负责验真与防篡改。JWT 编码不等于加密。旧 License 外层 RSA 解密也不能替代内部 RS256 授权验签。

实现边界与代码依据

Gateway 基准 v1.6.0@8f9390b0：DshEntitlementService、DshServiceAuth、DshJwtService。桌面凭据：src/main/enterprise/secure-credential-vault.ts。

当前 HMAC 正文上限 64 KiB，不能直接用于整份大文件。知识上传使用 v2 认证与流式转发，另行限制大小、校验内容，不聚合整份文件做 HMAC。

HMAC 是服务间共享密钥认证，不能作为厂商授权签名的替代品。未假定已有 mTLS 或额外应用层 AES 正文加密。

03 / DSH 统一准入时序

  1. Work → 企业 SSO

    系统浏览器完成登录，使用一次性身份票据 + PKCE；Work 主进程核对登录 state。

  2. Work → Gateway

    提交票据与 PKCE verifier。Gateway 校验并通过内部签名调用向 Bisheng 兑换真实员工身份，确认已分配席位。

  3. Gateway → Work

    签发短期 access token 与轮换 refresh token。主进程保管凭据，插件仅获得连接状态。

  4. Work → Gateway

    所有 DSH 业务先经过统一过滤器：token 签名 / 用途 / 有效期 → 当前 session 与 grant_version → DSH 授权与有效席位 → 路由声明的功能 bit。授权依赖不可用则拒绝。

  5. Gateway → Bisheng

    剥离客户端身份头与桌面 Authorization；知识库改用专用服务账号 Bearer，并从已认证会话生成 X-On-Behalf-Of。Bisheng 检查 delegate 范围、员工有效性和 ACL；模型内部入口采用可信服务调用合同。

  6. Bisheng → Work

    经 Gateway 返回可见片段与引用，由当前 Agent 生成回答；打开引用再次鉴权，上传额外校验写权限。

登录 / 票据兑换采用 PKCE 策略；刷新采用 refresh 策略；注销验证凭据归属；内部接口采用服务认证，不能统一要求已有 access + 席位。普通业务使用完整准入链，控制接口逐项声明适用检查。

现状 → 目标
现状：模型请求透传到 Bisheng 后，再回调 Gateway introspect 检查席位。
目标：Gateway 在业务转发前完成统一准入；Bisheng 保留可信调用验证与资源权限，不再要求每个业务接口重复回调席位检查。
Token 兼容性

现有桌面 access token 使用 HS256，audience 为 bisheng-dsh-model。不能直接当知识 API token 使用；实施时须版本化扩展用途与校验合同，知识路由拒绝旧模型 token。refresh 轮换沿用现有重用检测。

04 / 授权规则与迁移边界

共享授权读取，分开判断

License 投影分别提供原有商业能力、DSH enabled / seat_limit、知识 API bit。RS256 是现有 DSH entitlement 机制，不代表原有商业 License 已全部使用该格式。

每条业务路由声明操作

模型要求模型能力；知识检索、上传与引用要求知识 API bit，读写区别由 v2 scope 和 ACL 判断。购买 bit 不代表开放所有 DSH 能力。

兼容但不留旁路

历史 DSH 地址与新增地址执行同一门禁。Bisheng DSH 源站限可信网关访问；普通 v2 仅接受自身凭据。Work 不持有可绕过门禁的 PAT 或服务密钥。

开通 Connect = 登录会话有效 ∧ 企业已购知识 API 权限 ∧ 当前用户有有效 Work 席位
实际访问 = 已开通 Connect ∧ Bisheng 当前资源权限。

拟新增权限 WORK_KNOWLEDGE_API，具体 bit 编号实施时确认。每次 API 调用由 Gateway 检查当前授权与席位；前端显示状态不能作为放行依据。

企业未购买

保留 Connect 入口，显示“企业未开通知识库 API”，联系管理员。

已购买、无席位

显示“尚未分配企业席位”，由管理员分配现有 Work 席位。

已购买、有席位

允许连接并选择可见空间。没有数据权限时显示“暂无可访问知识库”。

v1.6.0 既有基础席位同样可满足席位条件，但不自动获得 API 购买权限。此授权针对 Work 企业接入；Bisheng 开源知识库能力保留。首期做检索与引用，上传随后接入同一认证链。

实施顺序与验收

① 盘点全部 DSH / 普通 / 旧商业路由并建立策略表；② 接入公共准入模块，覆盖历史入口；③ 增加知识 bit 和 v2 委托适配；④ 完成旁路封堵后迁移 Bisheng 重复 introspect。

验证普通 v2 不受 DSH 撤席影响、DSH 缺席位与缺 bit 被拒、旧地址不能绕过、商业 License 到期不阻断免费核心、内部接口拒绝伪造身份、未登记 DSH 路由拒绝。新请求检查当前撤权状态；流式请求建立后撤权须另定取消策略。

现有 DshRoutes 清单不能当作完整权限注册表。WebFilter 覆盖 Gateway Controller，代理业务在转发前使用同一准入服务；仅增加路由 GlobalFilter 无法覆盖所有本地 Controller。上传不得沿用普通路由的正文聚合配置。
