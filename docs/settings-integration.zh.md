# DSH 设置与 Bisheng 整合

## 当前界面

面向企业普通员工，简洁易用，沿用原本 DSH / Harness 框架。

- 侧栏底部显示当前账号；菜单顺序为设置、审批、连接手机、退出登录。设置快捷键继续直接打开设置，展开账号菜单不改变聊天显示或路由。
- 设置使用 DSH 默认的平级导航、通用设置行、标题操作和插件页签。模型、Agent 预设、执行偏好、插件清单与第三方贡献直接可达，不另加高级设置折叠层。
- Bisheng 通过既有扩展点加入账号与安全、用量与存储、按权限开放的个人 AI 接入及关于与帮助。企业模型列表与恢复入口直接展示。
- 审批属于独立面板，包含我的审批、我的申请和通知，不注册为设置页。

## 组件与数据归属

`dsh-desktop-settings` 复用 Harness 0.2.0-rc.2 已有的 single/root `settings.launcher`，账号菜单使用 UI primitives 的 Menu / MenuItemButton，审批使用 Modal。不再向 `settings.navigation`、`settings.general.layout`、`settings.actions.layout`、`settings.plugins.layout` 注册布局贡献，直接使用 owner 的默认 fallback；既有兼容接缝未在本次变更中修改。

DSH 原生组件与各 feature-owned rows 保持原挂载位置及生命周期，不复制设置组件、不移动 React DOM、不改变 slot 竞争规则。设置状态仍由 Harness 服务持有，企业身份由主进程企业服务管理，账号资料和云端用量仍由 Bisheng 后端维护，不迁移用户配置。

账号读取与退出调用既有固定端点，读取有取消与版本检查，退出失败保留账号及重试入口。账号菜单持有独立审批可见状态，唯一 Chat/Work presenter 负责原生网页区域；区域 token 防止旧组件的卸载清理影响新面板。关闭审批后恢复原页面及账号入口焦点，Tab 可在原生页签、内容和关闭按钮间交接。

手机连接通过窄 preload 方法消费既有配对 IPC，主进程验证可信主窗口及主 frame。账号菜单出现时移除旧手机按钮及其布局样式；Safe Mode 或未加载该可选插件时保留原设置与手机入口。未登录时本机设置和手机配对仍可用，企业操作禁用。

## 网页内容模式

账号、用量、个人接入以及三类审批/通知内容复用现有隔离 WebContentsView 和 cookie session。网页仅在原生嵌入且 `dshSettings=1` 时采用内容模式；独立浏览器保留原设置布局及语言偏好。退出、凭据、文件和进程能力继续由宿主持有，网页不获得通用 IPC。

主进程通过 `settingsProtocolVersion: 1` 声明内容协议，宿主贡献与唯一几何 presenter 均检查版本。内容挂载后，网页通过受限 preload 报告就绪；主进程核对 origin、主 frame、实际路径、分区、查询参数和身份 generation 后才显示。完整导航或离开设置路径后撤销就绪状态，重新加载必须重新报告。旧宿主或旧网页缺少协议时显示兼容提示，不把先前的聊天或知识空间显示到设置区域。

设置和审批关闭后恢复进入前的聊天/模块路由。网络、导航及就绪失败保留服务诊断，提供重试与返回本机设置；Safe Mode 不依赖企业功能。插件仍按当前 Desktop 安装入口投影，不改变 launch-root、Profile、宿主 fallback 或 bootstrap 顺序。
